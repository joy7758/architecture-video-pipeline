## 2. 为什么与照片不一样

本轮实际查看两张用户原图、交付封面、视频抽帧及模型源码。相机尚未匹配照片，因此以下视觉差异用于定位返工部位，不是测绘误差百分比。照片有夕阳、后期和透视影响，不能直接把色值或像素宽度当成真实尺寸。

| 部位 | 参考照片与交付的可见差异 | 追溯与判断 |
|---|---|---|
| 顶层屋盖与抱厦 | 照片中主屋面、前部抱厦及檐下形成密集的前后层次；交付中主屋面较平整、前伸层次弱，顶层柱廊更空 | roof 工厂和顶层参数需固定机位对照；不能只检查“存在抱厦” |
| 檐下和楼层承托 | 照片的斗栱、彩绘、梁枋有密集深浅层次；成片表现为重复窄色带、稀疏短支承，门窗大面占主导 | 新 roof.ts 只保留短椽尾；完整檩椽未继承。guanque 的重复斗栱不足以证明照片层次一致 |
| 栏杆与立面关系 | 成片两圈浅白栏杆很抢眼，周围暖木色、深色承托与彩绘层次偏少；照片栏杆更融入密集立面 | 同时涉及造型、材质、照明与输出距离；不能仅靠把颜色调暗关闭 |
| 台基与阶梯 | 保留了大轮廓，但成片石墙、踏步、栏杆和转折处理重复而整齐；照片有更丰富的墙面分格、装饰及场地关系 | 现有台基为简化程序模型；“高台+分段楼梯”只证明类型识别，不证明具体建筑匹配 |
| 整体比例 | 当前代码部分尺寸按 0.4 单位/米换算，屋顶高程仍为照片估计；成片俯视角与原图不同，台基画面份量大 | 台基/楼身比与用户资料比相差约 0.13%，未发现总高录错；仍需匹配相机核对各层组合与檐口位置，不给未经标定的实物误差数值 |

可追溯源码：`app/src/heritage/guanque.ts:11-27`（艺术单位与照片估计）、`roof.ts:175-179`（整张屋面/底面）、`roof.ts:247-263`（短椽尾）、`guanque.ts:59-85`（重复斗栱）、`materials.ts`（程序材质）。R3 文档已承认这些限制并标记待验收，见 `docs/photo-comparison-r3.md:3,52-64`。详细部位补充见 `building-findings.md`。

只读几何计算另有两个结果：台基/楼身比为 `6.6 / 22.9904503 = 0.2870757`，用户资料 `16.5 / 57.4 = 0.2874564`；比率相差约 0.13% 仅说明代码与用户数字一致，绝非实景复原精度。抱厦请求 rise=1.18，内部肩高钳制后实际为 0.9568846，比配置小约 18.91%；这是确定的实现行为，尚不能当作实物高度误差。原始结果与只读复现方法见 [geometry-observations.json](geometry-observations.json) / [geometry-observations.mjs](geometry-observations.mjs)。

## 3. 为什么与 GitHub 视频不一样

实际审查原始 `assets/preview.mp4` 的 0/3/6/10/14/19 秒，以及交付 0/6/9/12/18/23.9 秒。抽帧不足以证明每一瞬间均合格；节奏判断结合原 App 时间线及本地导出配置。

| 维度 | 原始演示 | 本次交付 | 偏差来源 |
|---|---|---|---|
| 容器 | 1280×740，19.575 秒屏幕录制，含网页控件，编码标称 120 fps | 1080×1920，24 秒，30 fps 纯视频 | 本地新增视频工位，Skill 本身没有视频导出器；编码帧率不等于画面独特帧率 |
| 过程 | 从底座开始，约 12.4 秒正向营造，之后观察成品 | 3 秒成品 → 6 秒倒放 → 12 秒正放 → 3 秒成品 | 本地导演脚本选择，未从演示冻结分镜合同 |
| 主体呈现 | 14 秒帧中建筑连同地坪约占画高 71% | 0 秒帧中建筑连同地坪约占画高 32% | 人工估读约 ±10px，只描述这两帧；纵横比和建筑形体不同，不能据此给出统一镜头倍率 |
| 相机 | starter overview FOV 34°（窄屏 39°），有飞檐/石狮视图控制 | 导出固定 48°，全程远距离环视、目标固定，未使用局部镜头 | 为避免台基裁切扩大相机距离，导致主体细节与装配运动更难看清 |
| 屋顶结构 | 原工厂有连续屋面/底面壳、整段椽和三道檩条 | 新工厂仍有连续壳面，但完整檩椽简化为短椽尾 | 更换几何工厂时简化了支承结构；连续壳面先出现本身并非新增退化 |
| 装配细节 | 原瓦片按行/列递进 | 新瓦片在约 .040 progress 窗内按确定性 noise 错开；牌匾用 visible 阈值开关 | 保留同一 shader 不能保证装配节奏相同 |
| 表面质感 | 木、砖、灰泥、绿瓦的材质对比较强 | 灰褐屋顶和浅石占主导；bump、金属度等也有改写 | 需按建筑照片决定色系，同时单独验收材质层次，不应照抄钟楼绿瓦 |

画面占比标记：原 14 秒约 y=127..656 / 740；交付 0 秒约 y=758..1364 / 1920，均含地坪，不含 UI/文字。属于人工抽帧观察，不是自动分割或摄影测量。

不能声称原始 preview.mp4 必然包含近景巡游：本轮抽帧看到的是全景营造与成品旋转。Skill 提供局部视图并要求局部验证，和“原视频实际展示了什么”是两类证据。

**现有 TITMAS 实现也不是照片保真审查器。** 本地 Owner 仓库 `/Volumes/ORICO_DATA/Projects/active/titmas-sandbox-gateway`，HEAD `a367c69b4d30a6e501dcaf4e52c65153e8a21f3a`，README 明示 schema preflight 不证明 Truth；`src/titmas_sandbox/validation.py:127-143` 执行 JSON schema 校验。其 `/sandbox/v0.1` 与前次公共 `/api/v1` 是不同入口；不能把本项目未接通扩大为所有 TITMAS 实现都不可用。它未来能验证证据/回执链，视觉推理仍需独立工位。

真正漏检发生在本地视觉验收：

1. 旧 `qa/visual-review.json:8` 范围为 `INDEPENDENT_ARTISTIC_PREVIEW_REVIEW`。PASS 理由是有高台、三层、檐线、完整画幅，同时承认比例/斗栱/彩画简化。
2. 源项目已是 `VISUAL_REVIEW_REQUIRED`，用户没有接受外观；复制进 job 的文字资料漏掉了后续纠错。结果却是 `visual:true`，交付清单只剩 TITMAS 阻塞。
3. CLI 主要验证文件存在、哈希和 reviewer 身份。两视角只要角度标签与图片 hash 不同；Skill 只看名称；模型只看非空字段；视觉 findings 甚至允许空数组。没有逐特征匹配、相机标定或未关闭问题门禁。
4. 源码快照与确定性渲染证明“输出稳定对应这些源码”，没有证明“源码对应用户照片和演示要求”。11 项控制测试也只证明控制协议行为，不能代替视觉审查。

因此，修复方向不是让 TITMAS 给当前画面盖章，而是先补建筑保真与演示表现两个独立验收条件，TITMAS 作为证据合同检查保留。
